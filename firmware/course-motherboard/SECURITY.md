# Security policy

## Supported versions

Before the first stable release, security fixes target the latest `main`. After tagged releases begin, the project will document which release lines receive fixes.

## Report a vulnerability privately

Do not open a public issue containing exploit details, credentials, device identifiers, private logs, or other sensitive information.

Use GitHub Private Vulnerability Reporting:

<https://github.com/CY-CHENYUE/easy-input-maker/security/advisories/new>

If private reporting is not yet enabled, use the “Request a private security contact” issue form. Do not include vulnerability details in that public request.

Include, when available:

- affected revision or release;
- affected feature and hardware path;
- reproducible steps or a minimal proof of concept;
- security impact and required preconditions;
- suggested mitigation;
- whether any credentials, personal data, or physical devices may already be exposed.

## Security scope

Examples include authentication bypass, unauthorized device control, credential exposure, insecure persistent storage, memory corruption, unsafe firmware update behavior, denial of service, and hardware actions that violate documented electrical or power constraints.

Ordinary bugs without a security impact should use the public bug report form.

## Disclosure

Please allow maintainers time to reproduce, assess, and prepare a fix before public disclosure. The project does not promise a fixed response time, but will keep the reporter informed when a private reporting channel is available.
